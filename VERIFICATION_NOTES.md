## Q1 — Did `next_milestone_days` change the meaning of "Keyingi marra"?

### Prior computation (before `81d48dd`)

From `git show 81d48dd^:frontend/src/components/library/WeeklyActivityWidget.tsx`:

```ts
const STREAK_MILESTONES = [3, 7, 14, 21, 30, 60, 100] as const

function nextMilestone(streak: number) {
  return STREAK_MILESTONES.find((m) => m > streak) ?? null
}

// in component:
const streak = computeStreak(activeKeys, today)
const milestone = nextMilestone(streak)
```

Rendered as:

```tsx
<span>Keyingi marra</span>
<strong>{milestone != null ? `${milestone} kun` : '—'}</strong>
```

### What that prior value represented

**Absolute next streak-length target** (the smallest entry in `STREAK_MILESTONES` strictly greater than the current streak), displayed as that target’s day count (e.g. streak 5 → `"7 kun"`).

It was **not**:

- days remaining until the streak breaks if idle today (`milestone - streak` would be 2 for streak 5 → next 7; the UI never showed that),
- days until “tomorrow” or any calendar event,
- badge-only milestones `(3, 7, 14, 30)` only — the list included `21`, `60`, `100`.

### What `next_milestone_days` represents after `81d48dd`

Server (`backend/library/activity.py`):

```python
STREAK_DISPLAY_MILESTONES = (3, 7, 14, 21, 30, 60, 100)

def next_streak_milestone_days(streak: int) -> int | None:
    for milestone in STREAK_DISPLAY_MILESTONES:
        if milestone > streak:
            return milestone
    return None

# in serialize_activity_stats:
'next_milestone_days': next_streak_milestone_days(streak),
```

Widget (authenticated path) now uses `activityStats.next_milestone_days` for the same `<strong>{milestone} kun</strong>` under "Keyingi marra"; guest/`null` still uses client `nextMilestone(clientStreak)`.

### Verdict

**SAME concept** (client → server move of the absolute next display milestone). Label still means “next streak length target,” not “days left to earn it.”

**Not** a SEMANTIC CHANGE of "Keyingi marra."

**Note (numeric, not semantic):** authenticated users may see a different number only when server `current_streak_days` differs from the old client `computeStreak` (different activity sources). Example: if client streak were 7 and server streak 5, old UI would show Keyingi marra `"14 kun"` and new UI `"7 kun"` — still “next absolute milestone,” with a different streak input by design of Fix 3 SSOT.

Concrete same-streak example: streak **5**, no activity today → both before and after show **Keyingi marra: `7 kun`** (next target is 7, not `2 kun` remaining).

## Q2 — How does migration `0024_readingprogress_finished_at` backfill?

### Exact file contents

```python
        migrations.RunPython(backfill_finished_at, noop_reverse),

```

### Implementation type

**(a) `RunPython`**, but the body is a single ORM **`.update(... F('updated_at'))`**, which Django emits as one SQL `UPDATE` (column copy), **not** a Python row-by-row loop and **not** `RunSQL`.

- Does **not** use `.iterator()`
- Does **not** load finished rows into Python memory
- Is a **bulk** in-database update

### Locking / duration (Postgres, estimate)

- `AddField(null=True)` with no non-null default is typically a cheap metadata `ALTER TABLE` on modern Postgres.
- Backfill: one `UPDATE library_readingprogress SET finished_at = updated_at WHERE status = 'finished' AND finished_at IS NULL`.
- That takes a **RowExclusiveLock** and locks **matching rows** for the duration of the statement (not a full `ACCESS EXCLUSIVE` table rewrite by itself). Concurrent reads continue; concurrent writes to those rows wait until the UPDATE finishes.
- Rough order-of-magnitude (idle DB, indexed `status`, SSD): on the order of **sub-second to a few seconds per ~10k finished rows**, and **seconds to low tens of seconds per ~100k**, depending on hardware/load — not a minute-scale lock for typical library sizes.

### Recommendation

**Safe as a normal deploy-time migration** for expected Libro.UZ scale (thousands to low hundreds of thousands of finished rows). Convert to a **batched/backgroundable** data migration only if production `status='finished'` counts are in the **multi-million** range or deploy windows cannot tolerate a multi-second write lock on hot progress rows. No change implemented in this pass.
